From agent traces to replay

As agentic systems spread, more teams need to answer different questions about them — and answering means both recording what an agent did and being able to replay it. Different questions need different data and different replay machinery; the right choice is a pairing, driven by your use case.

A dataset built to characterize inference infrastructure load looks nothing like one built to study human-agent interaction, which looks nothing like one built for a replayable behavior record. Very few of the public corpora that exist today are shaped anything like one another — pick one that "has agent traces" and you can still discover it can't answer your question, because it was never built to.

But the dataset is only half the decision. A trace is inert until something replays it, and the replay mechanism decides what you can actually do with what the dataset kept. A rich trace that no tool can replay the way you need is a dead end; a capable mechanism can't reconstruct detail the trace already threw away. So the real question isn't "which dataset" but "which dataset and which mechanism" — and the answer depends on what you're trying to learn.

This post is a survey of that fragmented field — but a deliberately scoped one. It covers the trace corpora the inference-serving world actually consumes: the ones a replay mechanism (Inference-Perf, AIPerf, GuideLLM, vLLM bench serve, SGLang bench_serving, NVIDIA DynoSim) can turn back into a live or simulated workload. For each, it asks what the dataset keeps, what it throws away, and which questions that leaves answerable. When you line them up, the differences turn out not to be cosmetic — the schema follows the goal, every time.

Concretely, the set below isn't hand-picked — it's what falls out of a mechanical sweep. We went to each of the six replay mechanisms mentioned above and collected every agentic-trace format it can natively load and re-run; the union of those is the list you see here.

Two words, pinned down first, because they aren't the same thing. A session is the actual run — a developer's coding session, or one benchmark task attempt. A trace is what a dataset captured and shipped of it. The gap is the whole story: WEKA has 8,000+ real sessions, but its traces hash the content away, so a rich session doesn't guarantee a rich trace. Each count below uses whichever unit that dataset counts in its own documentation.

None of these are wrong on their own terms. WEKA and TraceLab hash content away because their question is "what request pattern hits the server." Mooncake keeps timing and prefix shape because KV-cache reuse is a scheduling problem, not a semantics one. Exgentic fixes the task set because its question is "model or scaffold," which needs uniformity more than realism.

Origin carries more weight than a skim gives it, and it's also the privacy story. You can't read provenance out of the records themselves — you have to know it going in. WEKA/AgentX, TraceLab, and Baseten are human-sourced, and the first two hash content away by design, so there's nothing session-identifying to leak; Mooncake's production traffic is handled at the infrastructure level rather than published with message content attached. Exgentic and SWE-smith sit at the other pole, entirely benchmark-generated — replayable by construction, no real person's data to protect, but no record of how anyone actually works either.

Where the datasets genuinely divide is on content. Exgentic and SWE-smith keep full request and response bodies; WEKA, TraceLab, and Mooncake keep token counts, timing, and prefix shape but discard the text. That asymmetry runs one way only: you can always throw content away to get the lightweight view, but you can never reconstruct content you didn't keep. For the infra questions those three were built for, dropping it is the right call. But it forecloses a whole class of questions permanently — why an agent went down a bad path, whether a prompt change helped. A token-count-only trace tells you a session was expensive, never why.

Two narrower differences are worth naming. Controlled comparability: Exgentic's fixed grid is what lets you ask whether a behavior came from the model, the scaffold, or the task — human-sourced corpora can't answer that, because real sessions aren't matched pairs.

And two fields only Exgentic records: tool definitions (every tool the model could have called, not just the one it picked) and request parameters (temperature, max_tokens, as sent). Most datasets tell you what happened; those tell you what could have happened — what counterfactual and tool-selection work needs.

From a trace file to a running workload: the replay mechanisms

A trace format is only half of the practical story. To benchmark a serving stack, something has to turn the recording back into requests. Here, replay does not always mean resending the original bytes. Some replay paths preserve a session's dependency graph and feed each live model response into the next turn; others preserve only arrival times, input and output lengths, or prefix-sharing relationships and generate substitute payloads with the same serving shape. Those are both useful experiments, but they answer different questions.

Inference-Perf, AIPerf, GuideLLM, vLLM bench serve, and SGLang bench_serving drive live inference endpoints, but their format-specific loaders do not necessarily preserve the same parts of a trace. DynoSim instead evaluates a simulated serving topology. Compare results only where the replay target, preserved trace properties, and reported metric align.

That boundary matters when reading benchmark results. Request-level throughput from two endpoint load generators can be compared if model, hardware, concurrency, timing policy, and payload construction are aligned. It is not directly comparable to end-to-end session latency from a causal graph replay, which includes dependency and branch effects. Nor is either number directly comparable to a DynoSim prediction, where no model is decoding tokens. The mechanisms can share a source trace without measuring the same system.

So which combination do you actually want?

If your question is… Use… Why
KV-cache / prefix-reuse scheduling research Mooncake Purpose-built for exactly this, at production scale, with the prefix/cache-hit signal as a first-class field — the only corpus here that treats it as one.
Load-testing or benchmarking inference infra under realistic agentic traffic, without needing conversation content WEKA / AgentX & TraceLab Both answer the same close-cousin question — infra load without content — at 8,000+ and 357K-round scale respectively; WEKA's hash is deterministically replayable, TraceLab's subagent nesting is only heuristically recovered.
Full-content agent trajectories for training or behavior analysis, without needing real-user provenance SWE-smith 5,017 benchmark-generated trajectories with full conversations and the resulting patch — full content like Exgentic, but from a single agent (SWE-agent) rather than a matched cross-model/scaffold grid.
Comparing models or scaffolds against each other, or debugging agent behavior from full message content Agent LLM Traces v2 The same task set run across five models and five scaffolds, with full request/response bodies — the only corpus here built for controlled cross-model/cross-scaffold comparison, and the only one recording tool definitions and request params.

None of these is a universal answer, and the gaps are specific: the infra-focused corpora don't keep content, the full-content ones don't record prefix/cache structure or standalone tool-call spans, and only one is built from matched runs. Pick on the question, not on record size.

Where to get them

Most are public today: Exgentic Agent LLM Traces v2, WEKA / AgentX, and SWE-smith on HuggingFace, and TraceLab and Mooncake on GitHub. Baseten Trace ships as an AIPerf loader format rather than a published corpus.

This post has been about what each corpus actually lets you learn — which questions it can and can't answer, given what it keeps. There's a separate question we haven't touched at all: how the underlying sessions came to exist in the first place — benchmark-generated like Exgentic and SWE-smith, recorded from real usage like WEKA/AgentX, or synthetically constructed like Mooncake's Poisson-filled 10%. That distinction changes what a dataset can honestly claim about the behavior its traces record, independent of how much any single trace captures. It's worth its own post — coming next.
