Recording what an agent did — and which format you actually want

As agentic systems become more prevalent, more people need to answer different questions about them — and gathering evidence to answer those questions means recording what an agent actually did. Different questions turn out to need very different data.

A dataset built to characterize inference infrastructure load looks nothing like one built to study human-agent interaction, which looks nothing like one built for a replayable behavior record. Very few of the public corpora that exist today are shaped anything like one another — pick one that "has agent traces" and you can still discover it can't answer your question, because it was never built to.

Our own team ships one of these corpora — Exgentic's Agent LLM Traces, introduced in [link: Exgentic Agent LLM Traces v2 blog post]. That post covers what's in the dataset and how it's built. This one starts from a different question: how does it sit next to everything else out there, and when should you reach for something other than it? When we lined it up against the rest of the field, the differences turned out not to be cosmetic. The schema follows the goal, every time.

This post is that placement exercise, written up so the next person doesn't have to redo it.

Starting from the thinnest end

Dataset Built for What's actually in it
WEKA / AgentX (SemiAnalysis) Inference-infra workload characterization Subagent traffic patterns and request shape from real human sessions — content is hashed away, because content was never the point
Mooncake (FAST'25) KV-cache reuse & scheduling research Production request traces from a real serving system — timing, token counts, prefix structure only; ~90% real traffic, ~10% explicitly synthetic (Poisson-generated arrivals, to fill gaps in the load model)
TraceLab Agent-serving infra (batching, latency) A replayable request-pattern corpus from real sessions — a load model, not a behavior record
SWE-chat Human–agent interaction research Full session content across several coding agents (Claude Code, Cursor, Codex, Gemini CLI) — human-sourced, with request/response bodies kept in full. Recorded live via Entire.io, an opt-in CLI that hooks into each agent natively and checkpoints sessions to git as they happen, then scraped from public repos afterward to assemble the published dataset

None of these are wrong or incomplete on their own terms. WEKA and TraceLab hash away conversation content because their question is "what request pattern hits the server," and content would just be noise for that. Mooncake keeps timing and prefix shape because KV-cache reuse is a scheduling problem, not a semantics problem.

The one dimension that's easy to miss on a skim: human vs. benchmark origin. SWE-chat, WEKA/AgentX, and TraceLab are all human-sourced. Mooncake is mixed.

Where Exgentic sits

The short version, for anyone who hasn't read [link: Exgentic Agent LLM Traces v2 blog post] yet: Exgentic keeps the full request and response body for every model call, not just a pass/fail score — recorded in OpenTelemetry GenAI format, at benchmark scale, across multiple agent scaffolds and frontier models. That's the detail that matters for this comparison: it's the only corpus here with nothing summarized away.

Full content plus timing plus subagent structure means the shapes the four thinner datasets above care about (request timing, token counts, prefix-sharing, subagent nesting) should all be derivable from Exgentic's fuller records, not the other way around. That's a reason to reach for Exgentic first if you're not sure yet which of the narrower questions you're actually asking — the fuller record can always be reduced down to what any of the others need; none of the others can be built back up into it. Exgentic is also the only one in this comparison that's deliberately, entirely benchmark-generated — a feature for its purpose (uniformity, scale, replayability), and a limit worth knowing before you reach for it to study how people actually work with agents — that's the one question a benchmark-generated corpus isn't designed to answer, no matter how full its records are.

So which one do you actually want?

If your question is… Use… Why
KV-cache / prefix-reuse scheduling research Mooncake or Exgentic Mooncake is purpose-built for exactly this, at production scale. Exgentic is a broader fit if Mooncake's production-only scope is too narrow — prefix and cache structure is derivable from its full content.
Load-testing or benchmarking inference infra under realistic agentic traffic, without needing conversation content WEKA / AgentX & TraceLab, or Exgentic WEKA/AgentX and TraceLab answer the same close-cousin question — infra load without content — at 8,000+ and 357K-round scale respectively; WEKA's hash is deterministically replayable, TraceLab's subagent nesting is only heuristically recovered. Exgentic carries the same traffic-shape signal inside its fuller record, plus content if the question grows beyond pure infra load.
Studying how people actually work with coding agents SWE-chat Human-sourced with full content, across 5,851 sessions spanning several coding agents. Exgentic isn't a fit here — benchmark-generated by design, so it can't answer a question about human behavior.
Debugging an agent, building an evaluator from real failures, or you're not yet sure which of the above you need Exgentic Full request/response bodies at benchmark scale, five models and five scaffolds to compare against.

Exgentic is named in every row on purpose — its full-content record is a superset of what the narrower corpora keep, so it's always at least a candidate.

This post has been about shape — which fields each corpus keeps, and which questions that answers. There's a second axis we haven't touched at all: how a trace corpus comes to exist in the first place — benchmark-generated like Exgentic, scraped from live sessions like SWE-chat, or synthetically constructed like Mooncake's Poisson-filled 10%. That distinction changes what a dataset can honestly claim about the behavior it records, independent of how rich its schema is. It's worth its own post — coming next.
