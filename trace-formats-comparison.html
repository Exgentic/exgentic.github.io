Recording what an agent did — and which dataset you actually want

As agentic systems become more prevalent, more people need to answer different questions about them — and gathering evidence to answer those questions means recording what an agent actually did. Different questions turn out to need very different data.

A dataset built to characterize inference infrastructure load looks nothing like one built to study human-agent interaction, which looks nothing like one built for a replayable behavior record. Very few of the public corpora that exist today are shaped anything like one another — pick one that "has agent traces" and you can still discover it can't answer your question, because it was never built to.

Our own team ships one of these corpora — Exgentic's Agent LLM Traces, introduced in [link: Exgentic Agent LLM Traces v2 blog post]. That post covers what's in the dataset and how it's built. This one starts from a different question: how does it sit next to everything else out there, and when should you reach for something other than it? When we lined it up against the rest of the field, the differences turned out not to be cosmetic. The schema follows the goal, every time.

This post is that placement exercise, written up so the next person doesn't have to redo it.

Starting from the thinnest end

Dataset Scale Origin Built for What's captured
WEKA / AgentX (SemiAnalysis) 8,000+ sessions Human, real usage Inference-infra workload characterization Subagent traffic patterns and request shape — content is hashed away, because content was never the point
Mooncake (Moonshot AI / FAST'25) 23,000 traces ~90% real, ~10% synthetic KV-cache reuse & scheduling research Production request traces from a real serving system (Kimi) — timing, token counts, prefix structure only; the synthetic slice is Poisson-generated arrivals filling gaps in the load model
TraceLab (University of Washington) 4,265 sessions Human, real usage Agent-serving infra (batching, latency) A replayable request-and-tool-call trace, built for serving-system analysis — content is stripped out, tool calls and cache-prefix structure are heuristically reconstructed rather than captured directly
SWE-chat (SALT-NLP) 5,851 sessions Human, real usage Human–agent interaction research Full session content across several coding agents (Claude Code, Cursor, Codex, Gemini CLI), with request/response bodies kept in full. Recorded via Entire.io, an opt-in CLI that hooks into each agent natively and checkpoints sessions to git as they happen, by developers who opted in to session logging; the published dataset was then collected from those public repositories

None of these are wrong or incomplete on their own terms. WEKA and TraceLab hash away conversation content because their question is "what request pattern hits the server," and content would just be noise for that. Mooncake keeps timing and prefix shape because KV-cache reuse is a scheduling problem, not a semantics problem.

The one dimension that's easy to miss on a skim, and one no schema field captures directly: human vs. benchmark origin — how a session actually came about. SWE-chat, WEKA/AgentX, and TraceLab are all human-sourced: real developers, real sessions. Mooncake is mixed — real production traffic from Moonshot AI's Kimi service, with roughly 10% of traces explicitly synthetic (Poisson-generated arrivals, filling gaps in the load model). Exgentic sits at the other end on purpose: entirely benchmark-generated, for reasons the next section gets into.

That same origin question is also the privacy question. WEKA and TraceLab hash conversation content away by design, so there's nothing session-identifying to leak. SWE-chat keeps full content from real developers, but it's opt-in — those developers chose to checkpoint their own sessions via Entire.io, knowingly. Mooncake's real traffic is production data from a live service, handled at the infrastructure level rather than published with message content attached. Exgentic sits outside this concern entirely, for a structural reason rather than a policy one: every session is benchmark-generated, so there's no real person's data in it to protect in the first place.

Where Exgentic sits

The short version, for anyone who hasn't read [link: Exgentic Agent LLM Traces v2 blog post] yet: Exgentic keeps the full request and response body for every model call, not just a pass/fail score — recorded in OpenTelemetry GenAI format, at benchmark scale, across multiple agent scaffolds and frontier models. That's the detail that matters for this comparison: it's the only corpus in this comparison organized around preserving complete model request and response bodies as benchmark-scale OpenTelemetry traces.

But the sharper differentiator isn't how much any single record holds — it's that every record was generated the same controlled way. Same tasks, same five scaffolds, same five models, same trace format, every time. SWE-chat has richer real-world context; TraceLab has richer serving-specific fields; WEKA has richer cache-topology fields. What none of them have is cross-model, cross-scaffold comparability on a shared task set — which is what you actually need to ask "does this behavior come from the model, or from the scaffold, or from the task," rather than just "what happened."

Full model request/response bodies plus timing plus subagent structure means most of what the thinner datasets above care about — request timing, token counts, message bodies — is already there in Exgentic's fuller records, not something you'd have to go elsewhere for. That's a reason to reach for Exgentic first if you're not sure yet which of the narrower questions you're actually asking. But "fuller" isn't "superset": Exgentic doesn't currently carry a prefix/cache-hit signal at all, and tool calls live inside the message content rather than as their own structured span — so for those two specific shapes, it's Mooncake/WEKA/TraceLab that have the field, not Exgentic. And Exgentic is also the only one in this comparison that's deliberately, entirely benchmark-generated — a feature for its purpose (uniformity, scale, replayability), and a limit worth knowing before you reach for it to study how people actually work with agents — that's the one question a benchmark-generated corpus isn't designed to answer, no matter how full its records are.

Two fields worth calling out specifically, because they're easy to skim past: tool definitions — the full set of tools the model could have called on a given turn, not just the one it picked — and request parameters — temperature, max_tokens, as actually sent. Most trace datasets tell you what happened; almost none tell you what could have happened, which is exactly what you need for counterfactual analysis, tool-selection research, or judging whether a model's behavior reflects the model or the sampling settings it was run under. Neither is a big, attention-grabbing field, but both are the kind of thing you only miss once you've needed it and it isn't there. And underneath all of this: recording in OpenTelemetry's GenAI semantic conventions, rather than a bespoke research schema, means Exgentic's traces plug into the tracing tooling teams already run — a practical advantage that's independent of how much content any given record carries.

So which one do you actually want?

If your question is… Use… Why
KV-cache / prefix-reuse scheduling research Mooncake Purpose-built for exactly this, at production scale, with the prefix/cache-hit signal as a first-class field. Exgentic isn't a fit here — it doesn't currently record a prefix or cache-hit signal at all.
Load-testing or benchmarking inference infra under realistic agentic traffic, without needing conversation content WEKA / AgentX & TraceLab Both answer the same close-cousin question — infra load without content — at 8,000+ and 357K-round scale respectively; WEKA's hash is deterministically replayable, TraceLab's subagent nesting is only heuristically recovered. Exgentic has timing and token counts but no dedicated tool-call span and no prefix/cache signal, so it's a weaker fit for infra load-shape specifically.
Studying how people actually work with coding agents SWE-chat Human-sourced with full content, across 5,851 sessions spanning several coding agents. Exgentic isn't a fit here — benchmark-generated by design, so it can't answer a question about human behavior.
Debugging an agent, building an evaluator from real failures, or you're not yet sure which of the above you need Exgentic Full model request/response bodies at benchmark scale, with the same tasks run across five models and five scaffolds — the only one here built for controlled cross-model/cross-scaffold comparison, for anything that starts from message content rather than infra-level traffic shape.

Exgentic isn't a universal answer — it wins on full model request/response bodies at controlled, comparable benchmark scale, but it's currently thin on exactly the two fields (prefix/cache structure, standalone tool-call spans) that the infra-focused corpora were purpose-built to capture.

This post has been about what each corpus actually lets you learn — which questions it can and can't answer, given what it keeps. There's a separate question we haven't touched at all: how a trace corpus comes to exist in the first place — benchmark-generated like Exgentic, scraped from live sessions like SWE-chat, or synthetically constructed like Mooncake's Poisson-filled 10%. That distinction changes what a dataset can honestly claim about the behavior it records, independent of how much it captures. It's worth its own post — coming next.
